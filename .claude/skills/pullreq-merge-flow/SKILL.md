# プルリクエストのレビューとマージ

このリポジトリの PR は、Codex のレビューで承認を得てからマージする。
レビューは自動では始まらず、承認の確認には順序と検査がある。
検査を飛ばした失敗は「レビューされていないリビジョンをマージした」という形をとり、その場では何も壊れないから、後からしか気付けない。
場面は三つに分かれる。レビューを依頼する、指摘に対応する、承認を検査してマージする。

## レビューの依頼

Codex は頼まれたときだけレビューする。
ドラフト解除をきっかけにした自動レビューはこのリポジトリでは無効なので、初回を含むすべてのレビューは `@codex review` コメントから始まる。

`@codex review` を投稿するのは Claude の役割である。
PR がドラフトでなくなり、チェックが green になったら投稿して待つ。
ドラフトを解除するかどうかは所有者の判断であり、Claude は解除しない。

進行と結果は `chatgpt-codex-connector[bot]` が PR に付けるリアクションでわかる。

- **👀**：レビュー実行中。終われば bot が取り下げるので、待つ以外にすることはない。
- **👍**：レビュー完了、指摘なし。
- 指摘があるときはリアクションではなくレビューコメントが届き、リアクションは残らない。

指摘なしの判定（以後**クリーンな判定**と呼ぶ）には、読んだリビジョンを `Reviewed commit: <sha>` で名指しする issue コメントが必ず伴う。
どのレビューも `@codex review` なしには走らないから、sha の記載を欠いた裸の 👍 はここには存在しない。

## 指摘への対応

指摘に対する修正を push したら、次の三つをこの順で行う。

1. 指摘のスレッドに、何をどう直したかを説明する返信を書く。
2. そのスレッドを resolve する。
3. 別のコメントとして `@codex review` を投稿し、再レビューを依頼する。

再依頼は省略できない。
👍 は push しても消えずに残るので、修正後のリビジョンは新しい 👍 を改めて獲得するしかない。
その理由が次の節のゲートである。

## マージの三つのゲート

`chatgpt-codex-connector[bot]` の 👍 は、それが残されたリビジョンに対するマージ承認である。
「👍 がある」だけを根拠にはできず、マージの前に三つを確かめる。

- **誰が残したか**：`chatgpt-codex-connector[bot]` 以外の 👍 は承認ではない。
- **どのリビジョンへの承認か**：👍 はコミットではなく PR に付き、ブランチが進んでも取り消されない。push の後にも古い 👍 は残って見つかり、それを根拠にマージすると Codex が読んでいないリビジョンが入る。判定が `Reviewed commit: <sha>` で名指すリビジョンが、現在の head であることを要求する。
- **その判定は何と言ったか**：以前のクリーンな判定が残した 👍 は、後のレビューが指摘を出しても残る。「👍 がある」と「最新の判定が head を名指している」が同時に成り立っていても、その最新の判定が指摘の一覧でありうる。最新の判定がクリーンな側であることを要求する。

判定の種類は本文のどこにも書かれていない。
クリーンな判定は issue コメントとして、指摘はレビューとして届く。
この経路の違いだけが種類の根拠なので、どちらの一覧から取り出したかを判定に添えて持ち回ることになる。

時刻をリビジョンの代わりにしない。
👍 の時刻と head コミットの `committer.date` を比べる検査は同等に見えるが、`committer.date` はコミットが書かれた時刻であって、ブランチがそれを受け取った時刻ではない。
手元でコミットを書いてから Codex に古い head をレビューさせ、👍 が付いた後で書き溜めていたコミットを push すると、古い 👍 のほうが新しい head の時刻より新しくなり、この検査は通ってしまう。
`Reviewed commit` は時刻ではなくリビジョンを名指すから、この隙間がない。

## ゲート検査の実行

検査は同梱のスクリプトで行う。
リポジトリのルートから:

    .claude/skills/pullreq-merge-flow/scripts/merge_gate.sh <PR番号>

三つのゲートをすべて通ると、検証済みの head sha を stdout に出して 0 で終わる。
どれかで止まると、理由を stderr に出して 1 で終わる。

必ずファイルか `bash -c` のスクリプトとして実行する。
対話シェルに行ごとに貼り付けると、`exit 1` が検査の中断ではなくシェルの終了になり、効かないままの `||` にも気付けない。

スクリプトには、素朴に書き直すと踏む罠への対処が入っている。
書き直すときは以下を守る。

- リアクション、コメント、レビューの一覧はどれもページングされる（リアクションは既定 30 件ずつ、他も最大 100 件ずつ）。1 ページ目だけを読むと、長引いた PR で最新の項目を取りこぼす。取りこぼしは「👍 がない」「古い sha を名指している」という顔で現れ、ループを壊さず静かに止めるので、失敗として名乗り出ない。
- head は一覧をすべて取り終えてから読む。先に読むと、一覧を歩いている間に届いた push が、置き換えられた直後のリビジョンへの承認として通ってしまう。
- 失敗したルックアップは「不明」であって「承認なし」ではない。API のエラーは配列ではなく JSON オブジェクトで返るので、空かどうかではなく型で検査して止める。パイプラインの末尾に jq を置くと途中の失敗が jq の正常終了に上書きされるから、各一覧は変数に取り切ってから読む。
- 判定が名指す sha は 10 桁の省略形である。「head がこの文字列で始まるか」は弱い問いで、別のコミットでも答えられる。commits エンドポイントで完全な sha に解決し、head との完全一致を要求する。解決できない省略形には GitHub が 422 を返し、それは不一致として落ちる。

未認証の API は毎時 60 リクエストまでで、検査 1 回はおよそ 5 リクエストを使うから、この上限は実際に当たる。
`GITHUB_TOKEN` があればスクリプトが Authorization ヘッダに載せ、上限は 5000 になる。
Claude Code セッションの中ではプロキシが `api.github.com` を認証するので、ヘッダの有無は結果を変えない。
`gh` の入った環境なら `gh api --paginate` が一覧歩きと認証とエラー時の失敗を引き受けるが、スクリプトが `curl` と `jq` で書かれているのは、素の環境にあるのがその二つだからである。

## マージの実行

ゲートを通ったことと、今も通っていることは別である。
検査の後に push が届けば、tip はもう検証していないリビジョンになっている。
だからマージは tip ではなく、検証したリビジョンを名指して行う。

REST のマージは `sha` を前提条件に取り、head が動いていれば GitHub が 409 で拒否する。
これが唯一の原子的な締めで、スクリプトの `--merge` がそれを行う。

    .claude/skills/pullreq-merge-flow/scripts/merge_gate.sh --merge <PR番号>

マージ方法はマージコミット（`merge_method: "merge"`）にする。既存の履歴がそうなっている。

Claude Code セッションの中では、この REST 呼び出しをプロキシが `403 Merging into a protected base branch is not permitted for this session type` で拒否する。
ブランチではなくセッション種別への拒否なので、設定を探しても解決しない。
この場合はゲートだけをスクリプトで通し、マージは GitHub MCP サーバの `merge_pull_request`（`merge_method: "merge"`）で行う。

`merge_pull_request` は `sha` を取らないので、検査の後に届いたリビジョンをサーバ側で拒む仕組みがない。
head を再読して比べるだけでも足りない。push の後の再読は新しいリビジョンを返し、それを比較相手にすればマージはそれを取ってしまう。
比較相手は必ず、ゲートを通した時点の値にする。

    verified=$(.claude/skills/pullreq-merge-flow/scripts/merge_gate.sh <PR番号>) || exit 1
    again=$(curl -sS "https://api.github.com/repos/takumin/mitamae-plugin-resource-gpg_keyring/pulls/<PR番号>" \
      | jq -r '.head.sha // empty')
    [ "$again" = "$verified" ] || { echo "no: head moved $verified -> ${again:-unknown}" >&2; exit 1; }
    # ここで初めて merge_pull_request を呼ぶ

これで窓は閉じず、比較と呼び出しの隙間まで狭まるだけである。
締め切れるのは `sha` 前提条件だけなので、REST が許される環境では `--merge` の側を使う。

## 判定を待つ間

リアクションはコメントやチェックと違って webhook では届かず、👍 は見に行ったときにだけ見える。
PR 本体のポーリングでも足りない。PR のペイロードも `issue_read` も、誰がリアクションしたかではなく数だけを返す。
一方でクリーンな判定に伴う `Reviewed commit` の issue コメント（指摘の場合はレビュー）はコメントとして届くので、遠隔セッションではその着信を合図にゲート検査を走らせればよい。
合図はあくまで合図であり、承認の判定はスクリプトの検査だけを根拠にする。
